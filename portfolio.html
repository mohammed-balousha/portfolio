What it replaces

Instead of showing a physical receipt, customers upload proof of their bank transfer from home. Instead of asking around, subscribers see price changes, generator status and announcements published by the provider.

Who uses it

  • Customers compare generators, subscribe, pay, review and send complaints.
  • Providers add generators, accept subscribers, set the ampere price, issue invoices and read revenue reports.
  • Admin manages users, complaints and announcements.

The core flow

  1. Provider sets upAdds a generator and the ampere price. US-30, US-14
  2. Customer subscribesFinds a generator and sends a request. The provider accepts it. US-04, US-07
  3. Customer paysTransfers at the bank, then uploads the proof. US-10
  4. Provider follows upIssues the monthly invoice and posts generator status. US-16, US-15
  5. Admin overseesHandles users, complaints and announcements. US-18 to US-20

How the delivery was planned

Seven weeks, five modules, and a gate at the end of each stage. Every module had tasks for UI/UX, front end, back end and mobile.

  1. Week 1: SRS approved
  2. Week 2: Database design and authentication
  3. Week 3: Customer module
  4. Week 4: Subscription and billing
  5. Week 5: Provider module
  6. Week 6: Admin module and notifications
  7. Week 7: Integration, testing, deployment and release v1.0
Fallback plan. If time ran short, the Admin module would be replaced by extra permissions for a super provider, so the core flow could still be delivered.

Where requirements meet code

Each module started as user stories with acceptance criteria. From those I wrote the task list for each discipline, so the designers, front-end, back-end and mobile developers worked from the same definition of done. Provider sign-up, for example, is gated by an admin-issued password, and that rule exists as a story with scenarios before it exists as code.

Five of the 31 user stories

Chosen because each one shows a real rule of the domain. The scenarios come from the project's original scenario list, rewritten here in Given, When, Then form.

US-07 Subscribe to a generator Customer

As a customer, I want to subscribe to a generator so that I can receive its service.

  • Given I am logged in and viewing a generator, when I press Subscribe, then a subscription request is sent to the provider.
  • Given a pending request, when the provider accepts it, then I become a subscriber of that generator.
  • Given I am not logged in, when I try to subscribe, then the system does not allow it.

Why it is here: the core flow, with an approval step between two roles.

US-10 Upload proof of payment Customer

As a customer, I want to upload proof of my bank transfer so that the provider can see my payment without a physical receipt.

  • Given I am logged in and have an amount due, when I upload the transfer notification, then the provider can view the proof.
  • Given I am not logged in, when I open the upload page, then access is denied.

Why it is here: a real-world constraint, paying by bank transfer, turned into a feature.

US-03 Provider registration Provider

As a provider, I want to register so that I can log in and manage my generators.

  • Given I enter the correct provider registration password, then I proceed to the registration form.
  • Given I enter a wrong password, then an error message appears.
  • Given mandatory fields are missing or invalid, then I am returned to the field to correct it.
  • Given all fields are valid, then I am sent to the login page.

Why it is here: role-based access. Provider sign-up is gated by a password the admin issues.

US-14 Set the ampere price Provider

As a provider, I want to set the ampere price so that customers can see it directly.

  • Given I am logged in as a provider, when I edit the ampere price and save, then the new price is shown to subscribers.

Why it is here: a change made by one role must show up for another.

US-15 Update generator status Provider

As a provider, I want to change the generator status so that users know when it is broken, in repair or stopped.

  • Given I am logged in as a provider, when I set the status and add a comment such as "in repair for 24 hours", then the message appears to my subscribers.

Why it is here: communication during outages, the moment subscribers care about most.
